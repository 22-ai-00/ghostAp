## Spec 通用任务与任务驱动专家审查

- 用户要求：Spec 不限于编程；写作包含思路、读者、编辑、审稿视角，其他任务先拆出领域专家，再进行多角色深查；保持其余自动执行和验收规则。
- 根因：Spec/Plan/Task/Build 提示默认软件工作；Review 以关键词分类后套固定角色组，容易把非编程任务按代码变更识别为编程。
- 修改：SpecArtifact 新增可持久化的 required_experts，每个角色包含名称、必要性、关注点和必查项。ReviewArtifacts 传递同一专家计划，Review 直接生成对应角色及稳定 role_id，不再用领域关键词选择模板。独立 completion_control、总角色上限、阻断建议规则和自动收敛逻辑继续保留。
- 角色推断在 SPEC 阶段完成。新生成、直接加载 JSON 和 discovery 后续工作项统一检查 3–7 个完整且名称归一化后互异的专家；不合格时保留原任务、工作目录和规格，自动修复一次，耗尽明确失败。旧数据仍可反序列化，真正执行前补齐专家。
- discovery 正常生成提示包含专家结构；解析失败的最小兜底不伪造通用角色，交给执行阶段进行真实推断。SPEC 只在校验通过后发送一次完成回调，合法直接加载也成对发送开始/完成事件。
- Spec/Plan/Task/Build 提示、BUILD 阶段名称和报告文案泛化为交付；写作提示明确要求创意/选题、目标读者、编辑、审稿/事实或论证核查四个独立视角。
- 回归覆盖：写作和陌生领域角色、结构化产物兼容、原任务修复上下文、重复/不完整/超量角色、直接加载与 discovery fallback、阶段完成回调。
- 验证：角色相关子集 68 passed；主代理补充执行 `uv run python -m pytest tests/test_spec_adaptive_roles.py -q`，退出码 0，7 passed。独立 verifier 运行角色/卡片/引擎/审查子集，退出码 0，70 passed；静态审查 PASS。相关 Ruff 与 `git diff --check` 均通过。
- 限制：尚未通过真实 ACP 后端执行写作任务或进行飞书租户实机验收；专家质量仍由后端根据任务推断，结构校验负责完整性与独立性，不替代事实判断。
