## Employee 恢复移出主服务 readiness

### 背景与决策

- 最新重启日志显示主进程从 `start begin` 到 readiness 约 55 秒，其中 `FeishuWSClient.start()` 在真正建立飞书 WebSocket 前同步等待 Employee Journal、数据/工作区、Actor/Team 与成员投影恢复约 23 秒。
- 主 Bot 审计 Journal 的打开与完整性校验继续保留在同步构造阶段：所有主 Bot 出站操作必须在网络派发前持久审计，不能为了加速制造未审计窗口。本轮因此只移动完整 Employee 恢复，不绕过 HMAC/hash-chain/Anchor 校验；195 MB 审计 Journal 的可信快照优化是独立后续项。
- 受管群 Registry 协调和 Slock 磁盘恢复仍在 WebSocket intake 前同步完成，保持 registry-first 入口授权合同；只有 Employee Runtime 恢复和成员远端审计改为真实连接后的单次后台 worker。

### 实现

- `FeishuWSClient._record_ws_activity("connected")` 先发布 restart readiness，再以 leaf lock 保证全进程只启动一次 `employee-runtime-recovery` daemon 线程；重连不会重复恢复，关闭后迟到的 connected 回调不会重新启动。
- worker 严格保持 `runtime.recover()` 后再执行 `reconcile_projected_memberships()` 的既有顺序。恢复未完成时 `runtime_recovery` readiness blocker 继续阻止 `/hire` 和员工执行，Shell、Codex 与普通主 Bot 路由不等待该 worker。
- 新增 `EmployeeDepartmentRuntime.fail_recovery()`：后台恢复或成员审计失败时关闭 Employee admission、记录 blocker，但不关闭包含主 Bot 审计 Writer 的 Runtime，避免员工失败拖垮普通回复。
- `FeishuWSClient.close()` 在销毁 Employee Writer/Vault 前有界等待 recovery worker；超时则返回 `False` 并保留共享依赖，防止恢复线程与资源关闭竞态。
- 通用 planning skill 默认生成的 `docs/superpowers/` 与仓库文档噪声门禁冲突；执行完成后按项目合同移除该临时计划目录，长期决策和证据记录在本节。

### 验证

- TDD 回归覆盖：主 readiness 不等待恢复、重连单次启动、恢复失败隔离、关闭后迟到连接、同步 Registry/Slock 与后台 Employee/membership 顺序、worker drain 超时保留资源、Employee admission 独立关闭。
- WS/受管群/Autonomous/文档与锁顺序扩大集：184 passed、17 subtests passed。
- 非慢速全量二次复验：12,977 passed、1 skipped、118 deselected、62 subtests passed；slow 分层：118 passed、12,978 deselected。两层均退出码 0。
- 修改文件 Ruff、`uv run python -m src.main --validate` 与 `git diff --check` 通过；仅出现 B054 已登记的两条 Lark SDK Python 3.13 弃用告警。

### 剩余风险

- 未重启当前生产进程，因此尚无真实租户墙钟复测；按日志分段预计 readiness 可提前约 23 秒，但同步构造仍会支付约 16 秒的 195 MB 主 Bot 审计全量校验成本。
