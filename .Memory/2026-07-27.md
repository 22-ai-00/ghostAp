# 主 Agent Slash Command 面板接入

## 官方契约与设计

- 对照飞书官方《飞书智能体支持 Slash Command》Markdown 文档确认：Channel SDK
  继续负责 `im.message.receive_v1` 长连接入站；Slash Command 面板通过
  `/open-apis/application/v7/app_slash_commands` 的 POST/GET/PATCH/DELETE
  OpenAPI 管理，用户选中后仍以普通 `/command args` 消息进入现有
  `SlashCommandParser` 路由，不需要增加新的 Channel 事件。
- 主应用需要发布
  `application:app_slash_command:read` 与
  `application:app_slash_command:write` 权限；PC 客户端最低 7.70、移动端最低
  7.71。单应用上限 100 条，创建/更新约 5 分钟生效，客户端另有约 3 分钟缓存。
- 复用员工 Bot 已经过真实租户响应修正的 `LarkSlashCommandAPI` 和
  `SlashCommandReconciler`，继续使用官方 `lark-oapi Client.arequest(BaseRequest)`
  与 tenant token，不手写 HTTP 鉴权。

## 实现

- 新增 `src/feishu/main_slash_commands.py`，注册 80 条主要命令，覆盖帮助、
  Coco/Claude/Aiden/Codex/Gemini/Traex/TTADK/TUI2ACP、项目与诊断、Deep、
  Spec、Worktree、Workflow、Slock 和持久数字员工。
- 菜单只放主要拼写，避免 `/enter_codex`、`/end_codex`、`/workflow`、Slock
  单字母别名等兼容入口挤占发现面板；这些别名的现有文本解析能力保持不变。
- `FeishuWSClient.start()` 在进入 Channel 重连循环前启动一次
  `main-slash-command-sync` daemon worker。首次创建 80 条命令不会阻塞主长连接；
  同一进程重连不会重复启动对账。
- 对账仍执行 GET → diff → POST/PATCH/DELETE → GET 精确验证；成功日志只记录
  total/created/updated/deleted 计数。缺 scope、API 超时或响应异常时只记录异常
  类型和补权限指引，不记录 token/服务端敏感消息，也不让现有 Bot 离线。
- README 补齐客户端版本、两个 scope、重新发布应用、100 条上限和 5+3 分钟
  生效/缓存说明。

# Codex 长任务历史失败终态误判修复

## 现场证据与根因

- 上一轮主 Agent Slash Command 任务的应用日志记录：
  `outcome=incomplete, stop_reason=end_turn, 事件数=13009, 最终长度=1999`。
  这说明 ACP transport 正常结束且最终回答不为空，但 GhostAP 把用户任务终态标成了
  未完成。
- 对应 Codex rollout 在 `14:10:11` 先写入完整最终回答，随后写入
  `task_complete`；该轮 112 个 tool call 全部存在配对 output，没有调用悬空，
  因而排除了模型提前停止、Channel 断连和 ACP 尾部事件丢失。
- 同一轮为了遵守 TDD 与系统化调试，共出现 17 次非零 shell 退出：
  14 次 exit 1、1 次 exit 130、2 次 exit 2，包括预期红灯和受限沙箱诊断。
  `@agentclientprotocol/codex-acp` 会按 exit code 把这些已结束调用映射成 ACP
  `status=failed`。
- `classify_prompt_result()` 旧逻辑要求历史中的每个 tool call 都必须为
  `completed`。因此任意一次已经调查并被后续验证覆盖的失败尝试，仍会永久触发
  “仍有工具调用未成功完成”；它混淆了“失败但已终止的历史尝试”和
  “仍未进入终态的未决工具”。

## 修复

- ACP 任务完成判定现在把 `completed` 与 `failed` 都视为工具终态。工具失败仍完整
  保留在卡片活动历史中，但不再仅凭历史失败覆盖最终 `end_turn`。
- `pending`、`in_progress`、空值和未来未知状态继续 fail closed；未完成计划、
  timeout、cancelled、refusal、异常和缺失 stop reason 的原有保护保持不变。
- 回归契约改为验证“工具必须进入终态”，并显式覆盖 completed、failed、pending、
  in_progress、未知、空字符串和 `None`。

# 普通编程子任务收敛为单主卡

## 现场问题与设计结论

- 飞书截图显示普通 Codex 主卡已经包含“并行子任务 · 1 个 · 完成 1”、子任务序号、
  工具与模型；随后仍额外发送一张绿色子任务卡，但子卡正文只有“已完成”、模型和
  耗时，没有独立产物、操作或上下文，信息与主卡重复。
- 根因是 `ProgrammingCardSession` 同时维护两条路径：把 agent/task/subagent 摘要
  写入主卡 `metadata.subagents`，又通过 `CardSessionFactory.create_subagent()`
  创建独立飞书消息并维护子卡终态。Deep 已采用单主卡，普通编程模式仍保留旧分卡
  契约。
- 设计按“没有信息增量就不增加层级”收敛：一个用户编程任务只保留一张主卡；子任务
  名称、序号、工具、模型和状态继续显示在主卡顶部，子代理文本/工具调用留在主执行
  流，图片进入主卡并用任务名标注。只有飞书容量分页可以创建续接卡。
- Before/After 预览：
  `ux/programming-subtasks-single-card.html`。`AGENTS.md` 的旧“子代理独立任务卡”
  规则已同步改为单主卡契约，避免后续回归。

## 实现

- `ProgrammingCardSession._handle_agent_task_event()` 不再创建或更新子
  `CardSession`，改为仅按稳定 tool call id 更新主卡子任务摘要；START/UPDATE
  保持 running，DONE 映射 completed/failed，父任务完成/失败/取消时收敛尚未终结
  的摘要状态。
- 删除普通编程 handler 的 `CardSessionFactory` 与 `create_subagent` 闭包，以及
  adapter 内已经不可达的子卡工厂、媒体 publisher、投递等待、abort 与终态生命周期。
  普通工具事件和主卡容量分页逻辑不变。
- 子任务图片统一由主卡 `ACPImagePublisher` 发布，并把任务名加到图片 alt/name；
  已完成后迟到的图片同样留在主卡。
