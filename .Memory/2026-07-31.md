# 2026-07-31

## 测试套件语义去重与快慢分层

### 现场与根因

- 初始清单有 701 个测试文件、11,589 个 AST 测试函数、273,220 行和 12,983 个 pytest collection item。AST 只找到 6 组完全相同函数体，均是刻意保留的 Deep/Spec 独立引擎或 Coco/TTADK 后端契约，不能按文本相似直接删除。
- 主要冗余来自语义层：命令和路由表通过参数化为每个等价输入重复创建重型 fixture，Workflow 对完整 action 注册表另做严格子集断言，部分测试复制生产公式或在测试内部手工模拟 handler，UI/错误格式也存在同一生产边界的重复样例。
- 默认快速层还收集了真实 sleep、子进程超时/回收、沙箱证明和租约续期契约。它们并非重复测试，但会把本应快速反馈的门禁变成墙钟等待。
- 审计时发现 `TimerScheduler.shutdown()` 只在 `join(timeout=2)` 前唤醒一次，却要到 `join()` 后才清理队列；调度线程醒来后会再次等待远期任务，资源清理因而稳定等待两秒，并可能留下仍存活线程。这是生产实现竞态，不应靠删测试隐藏。

### 变更

- 将命令目录、命令注册、Workflow action 和 WebSocket 路由的等价参数改为单测试内表驱动循环；保留所有原始输入及逐输入失败诊断，同时让重型 client/registry fixture 只构造一次。
- 删除严格被完整注册表、规范格式器、真实 handler、redaction/error 规范套件覆盖的子集断言，以及复制生产公式和手工模拟分支的伪契约。
- 保留安全、授权、并发、Journal/effect、恢复、持久化、外部协议以及 Deep/Spec、Coco/TTADK 的独立契约；6 组精确重复函数体数量保持不变。
- 把 17 个经实测超过一秒、且必须依赖真实进程或墙钟的用例标记为既有 `slow` 层。测试未删除，完整发布门禁仍会全部运行。
- `TimerScheduler` 增加 shutdown fence：先发布关闭状态，再在锁内取消 scheduler event、清空队列，随后唤醒工作线程并等待退出；调度与关闭竞态会在同一锁下拒绝新任务。新增远期定时器快速退出、回调不执行和 schedule/shutdown 竞态回归。

### 结果与验证

- 最终清单为 701 个文件、11,541 个 AST 测试函数、272,869 行和 12,753 个 collection item；净减 230 个收集项、48 个函数和 351 行，未增加精确重复组。
- 默认快速层：`uv run python -m pytest tests/ -q -m "not slow"` 为 12,626 passed、9 skipped、118 deselected、45 subtests passed，耗时 460.81 秒。
- 慢速层：`uv run python -m pytest tests/ -q -m slow` 为 118 passed、12,635 deselected，耗时 630.11 秒；新标记的 17 项单独验证为 17 passed。
- 命令/路由和删除项的 canonical owners 为 219 passed；Timer/resource cleanup 为 24 passed；卡片边界为 325 passed；Workflow 相关为 184 passed。
- `uv run python scripts/test_inventory.py tests/`、全量 collection、`uv run python -m src.main --validate`、全部改动 Python 文件 Ruff 和 `git diff --check` 均通过。只保留两条固定版本 `lark_channel` 第三方 deprecation warning。

### 后续风险

- 快速层仍约 7 分 40 秒；后续若继续优化，应优先对剩余真实时间契约引入 fake clock 或更轻的进程夹具，不能以删除安全/恢复边界换速度。
- 慢速层约 10 分 30 秒，仍是发布门禁的一部分；本次只改变调度层级，没有降低完整测试覆盖。

## 任务耗时与 Workflow 选择复审补强

### 变更

- TTL、强制关闭和审批拒绝路径统一在终态事件中携带会话时钟，使页脚在超时、拒绝及强制收口时冻结真实耗时。
- Worktree 的 `completed_empty` 纳入终态冻结；若随后收到合法进度恢复事件，则清除旧冻结值并继续按原会话起点计时。
- 活跃 CardKit `element_content` 流式更新时，页面签名忽略仅由秒数变化造成的页脚差异，避免每秒变化迫使整卡 PATCH；工具、模型和状态仍参与全局签名，下一次正常全卡更新仍渲染最新耗时。
- Workflow 评审选择恢复严格互斥：显式打开/选择评审会关闭 Auto，启用 Auto 会清空显式评审和面板；旧快照同时含两种状态时按显式评审规范化。重复选择 Traex 后模型面板仍保持可继续添加。

### 验证

- 页脚、终态、投递、Session、Worktree 和 Workflow renderer 针对性回归 325 passed。
- Workflow 选择与相邻处理器回归 184 passed；覆盖“第一个 Traex → 第二个不同模型 → 完成”、Auto/显式评审互斥、picker callback 和旧状态恢复。
- 回归证明仅耗时秒数变化不改变活跃流式页签名，而工具或模型变化仍会触发完整签名变化；未新增独立 heartbeat 或飞书 API 调用。

### 后续风险

- 运行中耗时仍随既有业务更新刷新，不承诺无事件时主动秒级 PATCH。
- 尚未在真实飞书租户完成卡片桌面/移动端和完整 Traex 重复选择链路验收；本地覆盖状态机、Card 2.0 JSON、分页签名与交付决策。

## Workflow 卡片重复推送与生命周期竞态修复

### 现场与根因

- `logs.log` 显示 05:18:58 评审结束、05:19:01 开始生成；随后到 05:21:55 约每 8 秒一次 generation heartbeat PATCH 均失败，累计 23 次 `main Bot patch recipient scope is unavailable`。05:22:01 生成超时后运行时启动，05:22:06–05:23:55 又约每 10 秒失败一次，且关停开始后仍继续出现。
- 首张 Workflow 选择卡没有把入站 `/wf` 的可信 `origin_message_id` 写入 `MessageLinker`，因此后续 PATCH 无法通过 main Bot recipient-scope 审计。旧进度回调在每次 PATCH 失败后又执行 `send_card_to_chat()`，把每个 heartbeat 都退化为一条新的飞书卡片；新卡同样没有 origin，形成永久失败循环。
- 深入并发审计还发现旧 selection/generation/queued-start 可在新请求后恢复、共享脚本路径可被旧生成覆盖、runtime bridge worker 可越过终态复用下一轮 engine 字段、selection finish 与按钮点击会丢更新、慢渲染可用旧卡覆盖新卡、cleanup retry 会丢失未完成 owner tombstone。这些问题会放大卡片重复、旧任务复活和状态串线。

### 变更

- 保持 main Bot outbound audit 默认拒绝，不放宽权限；首张选择卡、生成卡、初始进度卡和有界终态 fallback 全程传递可信 origin。周期性 generation/runtime progress 只允许 PATCH，失败时不再 CREATE；终态替代卡最多创建一次。
- 引入 session-keyed lifecycle owner，统一 selection、生成、卡片投递、排队启动和 runtime 终态。stop/cancel/supersede 会设置同一 stop fence、停止 heartbeat、等待在途投递并只清理 owner 自己的脚本。
- 同一发起者或管理员的新 `/wf` 采用 newest-wins：旧的未完成 selection、生成和未 claim 的 queued start 可直接撤销，只保留最新任务；已经 claim 的真实 runtime 不被隐式替换，仍需显式停止，避免共享 bridge/executor 未静默前复入。
- 生成脚本改为 session 唯一源文件，确认执行使用只读语义的唯一临时副本；取消/失败只删除本 owner 的产物，成功源文件保留到下一次 Workflow admission，继续支持 `/wf_save`。
- RuntimeBridge 在 stop 后关闭新提交门、终止 Node、等待 agent/subworkflow future 和 AgentExecutor 真正静默后才发布 IDLE。静默失败时 engine 保持 STOPPING tombstone；started/preclaim owner 通过持久 retired-owner 集合跨多次 cleanup 保留，直到真实 `done_event`。
- selection mutation、finish snapshot 和状态迁移统一采用 engine → selection 锁序；legacy confirm 同一 CAS 内读取工具并迁移状态。卡片投递比较本次 render snapshot 与当前 snapshot，并持联合锁更新，慢 S1 不会覆盖较新 S2。
- 新增确定性 barrier 回归，覆盖 PATCH 失败不 CREATE、origin 链接、stale callback/newest-wins、cancel/stop/confirm 竞态、唯一 artifact、bridge worker drain、queued preclaim cleanup、重复 manager cleanup、finish/select、legacy confirm/select 及乱序卡片渲染。

### 验证

- `uv run pytest tests/test_workflow*.py -q`：929 passed、8 skipped、45 subtests passed。
- `uv run python -m pytest tests/ -q -m "not slow"`：12,664 passed、9 skipped、118 deselected、45 subtests passed，耗时 460.82 秒。
- 生命周期/确认/选择定向复核 150 passed；selection/card 独立终审 145 passed；queued cleanup 双重回归 2 passed。两轮并发终审最终均为 Ready，无 Critical/Important 遗留。
- `uv run python -m src.main --validate`、`uv run python scripts/test_inventory.py tests/`、全部改动 Python 文件 Ruff 和 `git diff --check` 通过。Inventory 为 703 个测试文件、11,579 个 AST 测试函数、6 组既有精确重复。

### 后续风险

- 尚未在真实飞书租户复演故障注入；本地回归已证明持续 PATCH 失败时周期进度不会创建新卡，且所有有界 fallback 都继承可信 origin。
- 仍保留固定版本 `lark-channel-sdk` 的两条 Python 3.13 上游弃用警告，沿用 B054 跟踪，不通过过滤器掩盖。
