## 飞书卡片回调彻底切换最新版 2.0

### 根因与替换范围

- 对照飞书官方 `card-callback-communication` 最新文档确认：事件应为
  `schema: "2.0"` + `card.action.trigger`；回调必须在 3 秒内返回；即时更新
  裸卡时必须使用 `card: {type: "raw", data: <Card JSON 2.0>}`，不能返回裸卡。
- 主 Bot 虽已注册 P2 callback，但 ACK/toast 仍返回临时 dict，出站入口还会接受
  schema-less/Card JSON 1.0，并把根级 `elements` 静默升级；仓库锁释放通知也仍是
  旧根级结构。这会形成“新版事件 + 旧卡更新”的混合协议。
- 新增纯 callback contract：只接受 `schema == "2.0"`、事件类型
  `card.action.trigger`、完整 action/context/消息与群坐标；所有响应统一为
  `P2CardActionTriggerResponse`。toast 使用 typed envelope，raw-card 更新强制
  `type=raw` 且 data 通过完整 Card JSON 2.0 门禁。
- `BaseHandler` 出站边界不再兼容旧卡：只接受完整 dict/JSON、精确 schema 2.0、
  `body.elements` 列表且禁止根级 `elements`。Workflow 的 `{header, elements}`
  继续只作为内部 renderer fragment，由 handler 显式组装为 2.0 后才能发送。
- 主 Bot 和 Employee Bot 均只注册 `register_p2_card_action_trigger`；Employee 自动
  注册 manifest 只声明 `card.action.trigger`。旧 `trigger_v1` 没有生产注册或 fallback。
- 回调 P2P 来源解析删除 Chat API 远程 fallback，只读取消息入站时保存的可信来源；
  缺失或不匹配时 fail-closed。由此 callback ACK 热路径不再被远程请求拖过官方
  3 秒窗口，部署前历史卡也按 breaking migration 视为只读。
- 动态核对 PyPI 后把官方 SDK 更新到当前最新版：`lark-channel-sdk==1.2.0`、
  `lark-oapi==1.7.2`；同步更新 uv lock 和 Employee Channel 的 wheel、安装 RECORD、
  runtime payload 三重完整性锁。
- README 与 CHANGELOG 明确部署动作：飞书开放平台只保留新版
  `card.action.trigger`，删除旧 callback/请求地址并发布应用版本。该控制台动作不由
  仓库代码代替。

## Workflow Agent Pool 选择提速与回调超时修复

### 根因与修复

- 现场日志显示 Agent Pool 每级选择都触发服务端回调；旧卡把工具、模型、Profile、Effort 四级下拉分别做成 callback，每次都经过项目串行调度、ACP 能力查询和整卡 PATCH。卡片更新前没有首击反馈，用户再次点击会命中去重提示“操作已受理，请勿重复点击”。
- 模型冷探测原本只在启动时预热 Codex，且多个工具顺序探测；切换 Traex、Claude 等未缓存工具时，单次选择可能承担完整 ACP 冷启动时间。
- 生产卡改用飞书原生 `form`：工具切换仍负责一次必要的模型目录刷新，模型/Profile/Effort 合并为后端声明的精确配置，在客户端本地选择，点击“添加 Agent”时通过 `form_value` 一次提交。常见添加路径由四次选择 PATCH 降为一次提交 PATCH；服务端仍按实时能力目录 fail-closed 校验，旧卡回调继续兼容。
- Workflow 卡片回调入队后立即返回“正在应用选择，卡片将自动更新”Toast，满足飞书 3 秒响应窗口并减少重复点击；重复事件仍由既有指纹去重。
- ACP 模型预热改为按工具并行；应用启动时并行预热 Claude/Aiden/Codex/Gemini/Traex，Coco 继续使用独立模型管理器预热。进入 Workflow 选择页时还会按项目 cwd 补充预热所有可用工具。

## 普通编程跨执行窗口自动续跑

### 根因与方案

- 原实现把一次 `run_prompt_with_continuation()` 的绝对 deadline 同时当成单次 ACP 调用窗口和整个用户任务 deadline。进入安全收尾后，即使结构化计划仍有未完成项，handler 也只能把结果映射为失败卡，无法继续任务。
- 新增任务级 `run_prompt_across_execution_windows()`：只对“确实进入 timeout finalization 且结果仍为 INCOMPLETE”的情况自动续开窗口；完成、用户取消、普通不完整/待授权和异常保持原终态语义。
- 每个窗口仍使用原有有界执行与安全收尾。旧 transport 必须先 poison、暂停活跃 Goal 并退休；随后 `ACPSessionManager.resume_retired_session()` 在 session-key 启动锁内确认没有并发新 owner，再用原 provider `session_id` 启动新 transport。
- 排查发现默认 `SessionStartupCoordinator` 虽接收 `session_id`，但非 injected-starter 路径没有调用 `load_session()`。现统一在启动边界校验/加载目标 provider session；恢复失败会关闭新 transport 并 fail closed，禁止空白会话冒充续跑。
- 跨窗口提示只回放原始用户任务，不携带 bridge 注入文本；明确不新增权限、不扩大任务范围，并要求从工作区、结构化计划和会话历史续做。
- 默认最多 4 个窗口，可通过 `PROGRAMMING_MAX_EXECUTION_WINDOWS` 配置 1–24。该上限把单窗口超时与任务终态分离，同时保留资源熔断；达到总上限时使用独立文案，不再伪装为首窗口失败。

### 验证

- TDD RED 依次证明缺少窗口监督器、CAS 恢复入口、handler 接线、配置字段，以及默认启动路径未真正加载 provider session；对应最小实现后全部 GREEN。
