## Employee 恢复移出主服务 readiness

### 背景与决策

- 最新重启日志显示主进程从 `start begin` 到 readiness 约 55 秒，其中 `FeishuWSClient.start()` 在真正建立飞书 WebSocket 前同步等待 Employee Journal、数据/工作区、Actor/Team 与成员投影恢复约 23 秒。
- 主 Bot 审计 Journal 的打开与完整性校验继续保留在同步构造阶段：所有主 Bot 出站操作必须在网络派发前持久审计，不能为了加速制造未审计窗口。本轮因此只移动完整 Employee 恢复，不绕过 HMAC/hash-chain/Anchor 校验；195 MB 审计 Journal 的可信快照优化是独立后续项。
- 受管群 Registry 协调和 Slock 磁盘恢复仍在 WebSocket intake 前同步完成，保持 registry-first 入口授权合同；只有 Employee Runtime 恢复和成员远端审计改为真实连接后的单次后台 worker。

### 实现

- `FeishuWSClient._record_ws_activity("connected")` 先发布 restart readiness，再以 leaf lock 保证全进程只启动一次 `employee-runtime-recovery` daemon 线程；重连不会重复恢复，关闭后迟到的 connected 回调不会重新启动。
- worker 严格保持 `runtime.recover()` 后再执行 `reconcile_projected_memberships()` 的既有顺序。恢复未完成时 `runtime_recovery` readiness blocker 继续阻止 `/hire` 和员工执行，Shell、Codex 与普通主 Bot 路由不等待该 worker。
- 新增 `EmployeeDepartmentRuntime.fail_recovery()`：后台恢复或成员审计失败时关闭 Employee admission、记录 blocker，但不关闭包含主 Bot 审计 Writer 的 Runtime，避免员工失败拖垮普通回复。
- `FeishuWSClient.close()` 在销毁 Employee Writer/Vault 前有界等待 recovery worker；超时则返回 `False` 并保留共享依赖，防止恢复线程与资源关闭竞态。
- 通用 planning skill 默认生成的 `docs/superpowers/` 与仓库文档噪声门禁冲突；执行完成后按项目合同移除该临时计划目录，长期决策和证据记录在本节。

### 验证

- TDD 回归覆盖：主 readiness 不等待恢复、重连单次启动、恢复失败隔离、关闭后迟到连接、同步 Registry/Slock 与后台 Employee/membership 顺序、worker drain 超时保留资源、Employee admission 独立关闭。
- WS/受管群/Autonomous/文档与锁顺序扩大集：184 passed、17 subtests passed。
- 非慢速全量二次复验：12,977 passed、1 skipped、118 deselected、62 subtests passed；slow 分层：118 passed、12,978 deselected。两层均退出码 0。
- 修改文件 Ruff、`uv run python -m src.main --validate` 与 `git diff --check` 通过；仅出现 B054 已登记的两条 Lark SDK Python 3.13 弃用告警。

## Deep 重复消息洪泛与单主卡收敛

### 根因与日志证据

- 最近一次 Deep 任务只有一次话题注册（`logs.log:16063`）和一次 ACP session 启动（`logs.log:16067`），不是任务被重复执行。
- `logs.log:16071-16116` 在 77 秒内连续记录 43 个不同卡片 ID 的 `99992354` stale binding；初始消息加 43 次替换，因此用户至少看到 44 条重复消息。
- Deep 在首个文本块前先投影任务/阶段，首卡因而通过 IM interactive message 创建；后续同结构文本更新却无条件走 CardKit element API，将 IM message ID 当成 CardKit entity ID，触发 `99992354`。stale 逻辑又对每个新替换消息继续 append，没有“替换代再失效”熔断，形成洪泛。CardKit entity 的全卡更新同时误用 IM patch，是同一运输身份混淆。

### 实现与维护收敛

- `PageBinding` 显式记录是否支持 element update：只有 CardKit streaming entity/reference 可做增量文本更新，IM message 在文本变化时使用全卡 patch。`FeishuCardAPIClient.update_card()` 也按已知运输身份分流到官方 CardKit `card.update` 或 IM `message.patch`。
- stale 恢复以“逻辑源页 → 当前物理替换页”记录代际：每个物理代最多 append 一次，替换页立即 stale 或后续再 stale 都返回 `stale_replacement_exhausted:99992354`；创建超时仍保留同页幂等重试，grow → compact 的新物理代仍有一次合法替换机会。
- Deep 删除每个子代理的 `TaskOrchestrator` 实例、子 CardSession 和卡片数上限分支；任务概览、子代理文本/思考/工具/图片都复用普通编程已有的 `ACPStreamBridge` 和主 `CardSession` 流，只有超过飞书卡片容量才创建续接卡。保留 Deep 自有的 cycle/phase、heartbeat、权威耗时、暂停/失败和上下文持久化语义。
- 协作 wrapper 失败但未创建 child 时，先物化 `TOOL_STARTED` 再发 `TOOL_FAILED`，与普通编程 reducer 合同一致；会话内 materialized tool ID 保留，相同终态重放不会生成重复工具块。
- 交互预览同步从三张“Deep 子任务独立卡”收敛为一张主卡示例。Deep 相关测试从 33 个收敛到 26 个；三个修改的测试文件合计净减 4 个测试函数、净减 1 行，新增仅保留运输分流、熔断代际、失败协作与单主卡边界。

### 验证

- TDD 回归先后观察到 IM 文本误走 element API、第二次 stale 继续建消息、terminal replacement 立即 stale、grow/compact 代际误伤、CardKit entity 误走 IM patch、失败 collaboration 孤立 `TOOL_FAILED` 被 reducer 丢弃和 terminal 重放复制工具块等红测试，修复后均转绿。

## 远程重启门禁测试隔离

### 发现与根因

- 部署前主机侧 `./restart.sh status` 确认服务仍由 `.venv/bin/python -m src.main` 运行；沙箱内因 PID namespace 看不到宿主进程，不能把沙箱内的“未运行”当成线上状态。
- `rr` 预检发现线上 participation 记录指向已退出的 pytest PID。时间戳与本轮全量测试一致，生产日志也记录了 `participation service PID is not alive`，说明不是重启脚本自身失效。
- `test_ws_client_start_reconnects_if_underlying_start_returns` 构造真实 `FeishuWSClient` 并调用 `start()`，但未隔离 `_CHECKOUT_ROOT` 和 `restart_gate_dir`；测试的 connected 回调因此把 pytest 进程发布为线上 ready participant，测试退出后留下死 PID。

### 修复与验证

- 回归测试现在同时使用 `tmp_path` checkout 和独立 restart gate，并断言客户端绑定到临时门禁；既覆盖真实重连路径，又不再修改生产 participation/generation 文件。
- 红灯复现分别证明：只改断言仍会触碰线上门禁，只改 gate 仍会被真实 checkout locator 固定；两项隔离同时生效后测试转绿，线上 participation 时间戳在复验前后保持不变。
- WS 重连、restart gate 与 restart script 相关套件共 119 passed；`restart.sh` 可执行且 bash 语法检查通过，历史日志确认 `rr` 的 detached worker 能完成 drain、停服、启动和 ready 闭环。
- 发布操作应在所有测试结束后，用当前真实服务 PID 重新 `publish_participation` + `mark_ready`，验证 snapshot 后再推送 `dev` 并触发 `./restart.sh rr`，避免再次把测试进程写回线上门禁。
