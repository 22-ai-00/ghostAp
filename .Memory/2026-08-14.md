## A2A 与 GhostAP 通信边界研究

- 对 A2A `v1.0.1`、wire protocol `1.0`、Python SDK `v1.1.2` 及官方样例完成一手来源
  调研；形成 `docs/research/a2a-ghostap-assessment.md` 的协议语义、安全、可靠性、
  代码接缝与分阶段迁移评估。
- 核心结论是 A2A 不替代 ACP：Employee 内部继续通过 ACP 驱动 Codex/TraeX 等
  backend，A2A 仅作为持久 Employee、远程/第三方 Agent 之间的任务与产物协议。
  `LLM + tool` 是 executor binding，不是完整 Agent 身份；A2A 也不负责 spawn/hire。
- 当前 `TeamBackend` 的 `submit/result/cancel` 是最小接入点；建议保留本地
  `_RuntimeTeamBackend`，新增受信的 remote A2A adapter，后续再评估 Workflow 冻结池中
  的远程成员，不改造 Direct/Deep/Spec 或 provider 内部临时 subagent。
- Journal 仍是唯一事实源；A2A `COMPLETED` 只是远程声明，产物锚定、本地验证和
  effect finalization 后才能完成。由于 Send Message 只是可选幂等，必须持久化
  assignment/message/task 映射并对不确定结果执行对账，不能盲目重试有副作用任务。
- 本轮只新增架构研究与记忆，未修改生产代码或依赖；ACP adapter `1.2.0` 与
  Python ACP SDK `0.12.0` 已在 2026-08-13 升级验证，本架构问题不是 ACP 版本落后导致。
