## 普通编程计划未完成时自动续做

### 现场与根因

- `logs.log` 中 2026-07-30 08:36:13–08:47:10 的 Codex 运行与用户截图一致：卡片请求均返回 200，ACP 以 `stop_reason=end_turn` 正常结束，约 10 分 49 秒，不是超时、watchdog、飞书投递或权限回调失败。
- 对应 rollout 只更新过一次计划，留下 28 个未完成项，随后用普通文本询问四项产品门禁并结束；运行期间没有未解决的 ACP permission 请求。
- 产品计划本身明确写着 DG-2 未批准时仍应继续 Tasks 1–15、17、21–26，因此模型过早停止了所有未受阻工作。
- `classify_prompt_result()` 正确地把 pending plan 判为 `INCOMPLETE`；问题在于普通编程 handler 只能把该结果直接映射成 `ProgrammingCardSession.fail()`，既没有同会话自动续做，也没有“仍需用户决定”的非失败终态。

### 变更

- 新增 `src/acp/continuation.py`：仅在自然 `end_turn + pending plan + 无非终态工具 + 未进入超时收尾` 时，在同一 ACP session 和原始绝对 deadline 内自动续做一次。
- 续做提示对原任务范围内安全、可逆的实现选择采用文档推荐项或最小安全默认值并记录理由；不新增凭据、发布、删除、不可逆副作用或 ACP/sandbox/tool 权限，但保留用户原请求已经明确授予的 commit/push 等精确权限。
- 两轮结果按工具 ID、tool result、modified files 和 token 证据聚合；第二轮缺少 `PLAN_UPDATE` 时继承上一轮计划，避免“事件缺失即完成”的假成功。
- `PromptAssessment` 增加未完成计划/工具计数，pending plan 仍保持 fail-closed，不以自动续做绕过完成判定。
- 流式与非流式 handler 共用同一 runner。流式续做继续写入同一张主卡，并在轮次边界关闭旧文本/推理块；自动续做后若仍只剩需要用户决定的事项，卡片进入 BLOCKED/等待确认而非 FAILED。
- BLOCKED 现在写入 `terminal_reason="blocked"`，在异步终态投递完成前即可拒绝晚到事件；类型域同步加入 `blocked`。
- 非流式超时替换路径跟踪 active session，外层异常收口会退休实际替换会话而不是原始死会话。

### 验证

- 编程 handler、卡片、reducer、替换会话定向：181 passed；handler/heartbeat 32 passed；补测后任务级复审通过。
- 整体三提交审查结论为 Ready to merge，Critical/Important/Minor 均为 0。
- `uv run python -m pytest tests/ -q -m "not slow"`：12,831 passed，9 skipped，101 deselected，45 subtests passed。
- `uv run python scripts/test_inventory.py tests/`：成功完成，700 个测试文件、11,553 个测试函数。
- `uv run python -m src.main --validate`、changed-file Ruff 与 `git diff --check` 均通过。
- 测试只保留两条既有 `lark_channel` 第三方 deprecation warning；配置校验同时提示现有 `slock_default_roles` 为空，但校验成功。

- 自动续做严格限制为一次；第二轮仍有 pending plan 时会如实等待用户输入，不会无限循环或伪装完成。

- 正文按已有 TextBlock、工具和来源边界渲染为 Card 2.0 默认展开 `collapsible_panel`；没有按标点或空行猜测段落，也没有为外观伪造 `interactive_container` 回调。Deep、Spec、Worktree、Workflow、Autonomous 与静态卡片保持原渲染。
- 子代理小标题动态使用最新安全任务简述；标题和并行摘要工具名会按原始 tool-call ID 清理 UUID/opaque ID，并遮蔽 OpenAI、GitLab、Slack、GitHub 等凭据形态及控制符/Markdown。CardKit `element_id` 与 block ID 解耦，保证字母开头且不超过 20 字符。
- 只有已登记在主卡子任务摘要中的来源才标注为子代理；Provider 给主 Agent 附带的普通 `source_id/agent_id` 仅用于哈希隔离文本流，不会误显示“子代理 · 子任务”。

- 嵌套流式签名只忽略当前选中的 `element_id` 正文；同页其他 active 来源仍参与签名并触发全卡 PATCH，避免第二路子代理增量被静默跳过。
- 分段文本使用与生产 `ensure_ascii=False` 一致的 UTF-8 预算和最坏 60 字中文标题外壳；单个超长段落会递归分页，解决中文正文过早产生一字续卡以及 remainder 超过 30KiB 的问题。

## Slock 空角色配置启动告警降级

### 现场与根因

- 当前 `.env` 未设置 `SLOCK_DEFAULT_ROLES`，因此 `Settings.slock_default_roles` 使用合法空默认值；该值明确表示不为新建旧 Slock 群自动创建预置角色。
- `Settings` 的 after-validator 却把这一合法 opt-out 状态记录为 `WARNING`。`Application.__init__()` 和 `--validate` 都在 `logging.basicConfig()` 之前构造配置，Python `lastResort` handler 因而把告警以无时间、无级别前缀的裸 stderr 输出，容易被用户或 Agent 误判为启动失败。
- `logs.log` 证明该提示与每次启动一一对应，但之后均正常发布 restart generation 并通过 readiness；`restart.sh` 只检查进程和 generation token，不扫描该日志文本。

### 变更

- 将空 `slock_default_roles` 的日志级别从 `WARNING` 降为 `INFO`，并把 validator 命名改为信息记录语义。
- 保留空配置的所有行为：不自动创建角色，不改变 Slock bootstrap、readiness、员工运行时或现有角色权限。
- 修正 `.env.example`：代码默认值是空且关闭自动建角，四角色组合是推荐示例，不再误写为代码默认值。
- 回归测试同时锁定日志级别和 `--validate` 成功路径不再向 stderr 泄漏该提示。

### 验证

- TDD 红灯：日志级别用例得到 `WARNING(30)` 而非 `INFO(20)`；subprocess `--validate` 成功退出但 stderr 含 `slock_default_roles is empty`。
- 修复后同两项回归：2 passed。
- 配置、Slock bootstrap、validate 与 Autonomous gate 相关套件：260 passed，仅保留两条第三方 `lark_channel` deprecation warning。
- `uv run python -m src.main --validate`：退出 0，输出直接从“配置校验通过”开始，不再出现裸 Slock 告警。
- changed-file Ruff 与 `git diff --check` 通过。

### 后续风险

- 旧 Slock 群若既没有持久化/手工角色又保持空配置，仍不会自动获得协作角色；这是保留的显式禁用语义，而非本次回归。
- 需要自动建角的部署仍应在 `.env` 显式设置 `SLOCK_DEFAULT_ROLES`；本次没有用代码默认值偷偷授予 `shell/file_write/git` 等角色权限。
