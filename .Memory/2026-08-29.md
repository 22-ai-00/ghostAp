# 2026-08-29

## Codex 未终态误判的严格对账与取证

### 现场结论

- 用户截图对应的父任务在 GhostAP 于 12:22:49 UTC 判定为
  `incomplete_tool_calls=4`：三个子代理卡片已经显示完成，另有一个
  `other:in_progress[-]` 外层调用阻断了最终任务状态。
- 原始 Codex rollout 显示父 turn 已在判定前完成，并且三个子代理均已有
  `task_complete`。这不是子代理实际挂起，而是 ACP 终态观察丢失后的假失败。
- 首个 `spawn_agent` 因 full-history fork 同时传入 `agent_type` 被 Codex
  在本地拒绝；它没有创建子代理，故若可严格关联，终态必须是 `failed`，不能
  标为 `completed`。

### 已落地修复

- 在首次 `classify_prompt_result()` 前执行 Codex 终态对账。对账仅接受唯一
  parent rollout、同 session/cwd、当前 turn 时间窗内的精确 `call_id`、唯一且
  后发生的 `function_call_output`；重复、越界、损坏或 ID 不同均保持未完成。
- 已知的协作 `spawn_agent` 拒绝输出映射为 `failed`；严格合法的
  `{"task_name":"/root/..."}` 输出才映射为 `completed`。这避免了把失败的
  spawn 误当成成功且无接收者的畸形调用。
- 子代理 rollout 生命周期在外层调用仍暂态时也会先做权威对账，因此截图中
  三个实际完成的子代理不会再因外层假未完成而被跳过。
- Codex 明确标记的 `contextCompaction` 仅作为内部 bookkeeping 排除出完成
  阻塞；只接受官方 Codex transport、精确布尔 marker、`other` 类型和暂态，
  不伪造工具完成，也不会跨 turn 继承该标记。
- 为最终仍未完成的 Codex 工具增加了仅日志可见的脱敏取证：SHA-256 截断 ID、
  allowlist 诊断和布尔状态；不会记录原始调用 ID、参数、内容、路径或子代理
  身份。

### 未完成的高优先级后续

  `commandExecution` 的 `item.id` 不同，`thread/read` 也不会保留这些 item。
