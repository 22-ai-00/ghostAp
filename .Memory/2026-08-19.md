## 普通编程切换为飞书原生 COT 过程消息

### 背景与范围

- 参考用户提供的 Feishu Message COT OpenAPI / AG-UI 说明，将普通编程模式原先卡片内的文本、过程摘要和工具调用迁移到原生 COT 消息。
- 保留 Card 2.0 作为任务事实与结果权威面：多任务列表、当前任务、并行 Agent 摘要、图片和最终结论继续使用现有主卡；Deep、Spec、Workflow 与 Employee 的结构化卡片及恢复契约均未改线。
- 在 `ux/programming-cot-hybrid.html` 增加运行中、完成态与降级态预览，先固定产品边界再接生产代码。

### 实现

- 新增 `src/feishu/cot.py`：
  - 使用官方 `lark-oapi` 的 `BaseRequest` / `Client.request` 通用入口调用 Create、Update、Complete；当前锁定的 `lark-oapi==1.7.2` 只有 `MessageCot` 数据模型，没有生成式 COT resource，请求未绕过官方 SDK 手写 HTTP。
  - 严格校验 HTTP、SDK 与业务三层响应；`events[].content` 做 AG-UI 要求的双层 JSON 编码，使用单调毫秒时间戳、稳定不透明 ID，并清洗工具内容与错误文本。
  - Create、Update、Complete 在网络前执行主 Bot 出站审计和 managed trust revision 双重栅栏；绑定冻结原消息、chat、message/cot ID 与别名来源。
  - 单任务 FIFO worker、有界队列与批处理只接受 TEXT、REASONING、TOOL 事件；PLAN、图片、AgentSummary 和终态结论不会误入 COT。
  - session 单请求预算为 2 秒，权威关闭总预算为 1.2 秒（显式最大 1.5 秒）；可选 COT 不再长期拖延最终卡。
  - SDK hard-timeout 保留 pending attempt，由固定后台池按原顺序处理晚成功；RUN_STARTED / Update 补 RUN_ERROR + Complete(error)，terminal 补 Complete，Complete 不盲重试。Create 已成功但响应 ID 丢失时因接口无幂等键或查询能力无法安全补偿，这是协议残余，当前禁止猜测性重试并自动使用卡片结果面。
  - abort 先本地 fence 再异步收尾；STARTING/close 竞态、队列排空超时、未发送多批事件和 worker append 失败均有唯一终态 owner，worker 不依赖调用方再次 complete/abort 才退出。
- 在 `src/card/protocols.py` 增加抽象 `ProcessEventSink`，`ProgrammingCardSession` 只依赖协议，不导入飞书实现。
- `ProgrammingCardSession` 采用 visible-first：先确认原主卡可见，再激活 COT；Create/RUN_STARTED 失败沿用同一卡继续流式执行，ACP 不重跑。
- COT 成功时过程事件进入原生消息，卡片只补最后一个非空主 Agent 结论；中途 Update、队列、Complete 或异步健康失败时，最多缓存 2048 个 / 2 MiB 已清洗 CardEvent 并原子精确回放到卡片，当前事件不重复。
- 处理器关联 origin、主卡和 COT 两个 message ID；COT 激活后的执行入口异常会同时 abort 卡片/COT、原异常透传，不触发非流式 ACP 重跑。
- 新增 `FEISHU_COT_ENABLED` 正式配置，默认开启；租户未开放能力时每个任务自动回退现有卡片，可用该开关紧急回滚。

### 后续风险

- 本地未持有真实租户的 COT capability，未做线上租户 smoke；无权限、未开放 endpoint 或 wire 不兼容都会在 2 秒预算内自动切回现有 Card 2.0，不影响 ACP 结果与结论交付。

## ACP 混合未完成状态按子代理优先续跑

### 根因

- 普通编程 Agent 自然 `end_turn` 时，续跑状态机原先只处理“仅有未完成计划”或“仅有未终态子代理”两种状态。
- 现场同时存在 `pending_plan_entries=3` 与 `unresolved_child_tool_calls=9`，两个互斥条件都不命中，因此 `automatic_continuations=0`，父任务直接以 incomplete 收口；卡片投影随后把仍未终态的子代理显示为“未收到最终结果，主任务已结束”。

### 修复

- `src/acp/continuation.py` 改为 child-first：只要所有未完成工具都来自子代理生命周期且没有外层工具仍在执行，就先进行一次权威状态对账，不再要求计划数为零。
- 对账轮严格限定为 `list_agents -> wait_agent -> list_agents`，禁止中止、取消、重复实施或改写原计划；一轮后仍有 running/pending 子代理时保持 incomplete，不让主 Agent 与活跃子代理重复工作。
- 每次 child reconciliation 都冻结并恢复进入该轮前的原计划，包括 `None`、已完成和 pending 三种状态。对账输出及会话证据 enrichment 均不能抹除旧计划，也不能凭空注入新计划。
- 子代理全部终态后才进入既有计划续做；继续沿用绝对 deadline、最多 1 次子代理对账和 3 次计划续做，避免无界循环。

- `uv run ruff check src/acp/continuation.py tests/test_acp_continuation.py` 与相关 `git diff --check` 通过。
- 回归覆盖 mixed→子代理终态→计划完成、子代理仍运行、外层工具仍运行、对账轮篡改/新增计划，以及 child 1 次 + plan 3 次的有界上限。
