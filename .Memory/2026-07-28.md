## 子任务失败详情默认折叠

### 背景与根因

- 现场截图中的独立子任务失败卡把 `CardEvent.failed(error)` 的完整错误字符串作为 `_error` 文本块直接渲染。
- 当错误是 `formatted_output` JSON、pytest 输出或调用栈时，文本块会直接占满正文并触发多页卡片；用户必须滚过大量诊断信息才能看到终态。
- 错误内容没有丢失或传输失败，问题位于卡片信息层级：详细诊断与摘要处于同一默认展开层。

### 修改

- 新增 `src/card/render/error.py`，从完整错误中提取稳定、单行的失败摘要：
  - pytest 输出优先提取 `FAILED <test-id>`；
  - 长 JSON 或不可读首行退化为“任务返回了较长的错误信息”；
  - 摘要经过单行标签清洗和长度限制，避免 raw JSON 污染面板标题。
- `src/card/render/renderer.py` 对终态为 `failed` 的子任务 `_error` 文本块使用红色 `collapsible_panel`：
  - `expanded=false`，完整 JSON、测试输出与调用栈默认收起；
  - 面板标题常显简短摘要和“已收起”状态；
  - 过长错误仍按原分页预算切分，每一段都保持折叠，诊断内容不丢失。
- 新增 `ux/subtask-error-collapse.html`，固化“摘要常显、详情按需展开”的 UI 预览。
- 新增回归测试覆盖长 JSON + pytest + 调用栈，验证所有错误面板默认折叠、标题不泄漏 `formatted_output`、完整错误仍存在于折叠内容中。

### 验证

- TDD 红灯：新增定向测试修复前失败，未找到错误折叠面板。
- 定向绿灯：`1 passed`。
- 相关回归：`192 passed`。
- 扩展卡片与编程模式测试：`1154 passed`。
- `uv run ruff check src/card/render/error.py src/card/render/renderer.py tests/test_card_renderer.py`：通过。
- `uv run python -m src.main --validate`：通过。

### 发布与风险

- 修改只作用于独立子任务失败块；主任务错误卡和正常结果卡不改变。
- 已经发出的历史卡片不会自动重写；服务重启后新产生或后续更新的子任务失败卡使用新样式。
- 折叠只改变默认视觉状态，不减少飞书卡片 JSON 的有效载荷；极长错误仍可能分页，但每页详情均保持收起。

## WF Loop Engineering 文档适配与运行时加固

### 文档研究与取舍

- 研究飞书知识库《Loop Engineering最佳实践-CC Dynamic Workflow》，重点对照确定性脚本编排、运行时/状态/推理分层、pipeline 与 barrier 语义、结构化节点契约、失败恢复和资源上限。
- 采纳并适配到 GhostAP 的部分：
  - 控制流继续由 JS 脚本显式表达，Python/Node runtime 只负责调度、状态、超时和恢复；
  - 同构多阶段任务使用 pipeline-first，只有下游需要全部结果时才设置 barrier；
  - 未知范围先用轻量 scout 限定 worklist，再进行有界并行；
  - 结构化输出是节点间的 fail-closed 契约，不能让未校验文本继续流向下游。
- 未照搬的部分：
  - 保留 GhostAP 的默认并发 10、硬上限 16、总 Agent 上限 200，不采用文档中的 1000 Agent 规模；
  - 保留现有 Dynamic Workflow 八类原语和独立调用 Journal key，本轮不引入 chained resume 协议；
  - 沿用紧凑 shape schema，不新增完整 JSON Schema 依赖或改动 `/wf` 三步交互。
- 详细实施边界、取舍与验证事实保留在本节；一次性实施计划已按仓库文档瘦身合约移除。

### 根因

- `parallel()` 已按 host `max_concurrent` 做有界调度，但 `pipeline()` 直接执行 `Promise.all(items.map(...))`，会一次性创建全部 item Promise；宽 worklist 会在 JS/JSON-RPC 边界制造突发请求和 backpressure。
- 结构化输出由 Python `AgentExecutor` 最多执行 1+2 次修复提示，但 Node `agent()` 收到失配结果后又会整层重试 3 次，最坏把一个节点放大为 9 次 Agent 调用。
- Python schema 校验只检查顶层 key，数组、布尔、数字和嵌套对象类型错误仍会被当成合法结构；重试耗尽后只保留 raw output、没有 error，失败节点可能继续进入下游。
- 脚本生成提示偏向“最大化并行”和高阶模式，没有明确 scope-first、pipeline-first 与 barrier 纪律。

### 修改

- `runtime/runtime.js`：
  - `pipeline()` 将每个 item 包装为 task 并复用 `parallel()` 调度，保持 item 间并行、item 内 stage 串行、输入结果顺序稳定，同时受 `max_concurrent` 限制；
  - 保留默认 fail-fast、in-flight Agent abort 和 `continueOnFailure` 局部错误返回；
  - JS 不再重复完整 schema Agent 调用，优先传播 Python 权威错误，并仅做一次递归 shape 防御校验。
- `executor.py`：
  - 紧凑 schema 改为递归类型校验，支持 type name/别名、JSON exemplar、嵌套 object、任意 array 和单元素 item schema；
  - number/integer 明确拒绝 boolean；
  - schema 修复重试耗尽后保留最后 raw output 供诊断，同时设置稳定 error 使节点 fail-close。
- `script_gen.py`：
  - 增加 Scope First、Pipeline-First、Barrier Discipline、Structured Output Contract；
  - pipeline 文案明确为受 `maxConcurrent` 限制的并行 map；
  - 最终生成要求由“最大化并行”改为“依赖允许时使用有界并行，禁止无界 fan-out”。
- 回归测试新增真实 Node runtime 并发计数和 schema 单调用验证，以及 Python 类型/嵌套 schema 契约。

### 验证

- TDD 红灯：新增契约最初 `5 failed`，分别捕获类型校验缺失、pipeline 无界 fan-out、schema 耗尽无 error 和提示策略缺失。
- 定向绿灯：schema、pipeline 语义和重试用例 `15 passed`。
- Node runtime 集成：
  - 4 个 pipeline item、`max_concurrent=2` 时观测最大同时 Agent 调用为 2；
  - host 返回 schema 失配时整层 `agent_call` 计数为 1；
  - 两项集成 `2 passed`。
- 运行时/容错/API/确认链路：`165 passed, 11 deselected, 37 subtests passed`。
- 全部非慢速 Workflow 回归：`952 passed, 8 skipped, 11664 deselected, 45 subtests passed`。
- `uv run ruff check ...`、`node --check src/workflow_engine/runtime/runtime.js`、`git diff --check`：通过。
- `uv run python -m src.main --validate`：配置校验通过。

### 风险与后续

- 收紧后的 schema 会把以前“key 存在但类型错误”的输出标记为失败；内置模板使用的 exemplar 形式已兼容，且完整 Workflow 回归通过。
- 当前 Journal 仍按单次 prompt/tool/model/role/schema 独立缓存，不具备文档所述的最长不变前缀恢复；若未来引入 chained key，应单独设计迁移和缓存失效契约。

## 团队员工事实、准入与重启恢复修复

### 现象与根因

- “团队成员现在都有谁”被宽泛的旧角色意图抢先匹配，查询的是 legacy `RoleRegistry`；真实员工已经存在于 Autonomous Journal，因此错误回复“当前没有角色”。
- “你们都能做什么”被当作可执行任务，Coordinator 又在确认可执行员工前写入任务事实并回复已受理；空 roster、通知失败和真实 Actor 已有终态在恢复时都可能退化成无响应或 `unknown_dispatch_outcome`。
- 进程关闭期间的 Channel monitor 仍可能继续 revalidate/submit，形成 ACTIVE → VALIDATING → PENDING → ACTION_REQUIRED 的错误尾序列；旧恢复逻辑无法证明这是关闭竞态，也不能安全自愈。
- NLI 同步桥在 fork 或启动超时窗口可能遗留错误 PID/loop/thread 所有权；Actor 重启恢复也缺少对“已提交终态但 sink 尚未完成”和 replay 期间新提交的完整围栏。

### 修改

- 团队查询与自然语言路由：
  - 当前群成员查询统一使用 Journal workforce 投影，按 tenant、chat、visible、non-archived 过滤；显式 `/roster` 继续展示租户全局花名册。
  - “团队成员都有谁”“你们都能做什么”等查询优先路由到当前团队能力卡；具体交付请求仍进入任务路径。
  - 成员存在、群关系、生命周期、Bot/Actor 运行态和接单能力分开展示；成员服务缺失或异常时保留持久员工可见，但默认标记“群关系待确认/不可接任务”。
  - 成员健康改为单次批量 Journal 快照，避免逐员工重复 replay；只有精确布尔 `False` 表示健康，缺失、异常及 `None/0/空串` 均 fail-closed。员工名、角色和能力按单行 Markdown literal 转义。
- 团队任务准入与通知：
  - Coordinator 在写 blob/Journal 和回复受理前先检查终态重复与可执行 roster；无人可接单时直接返回可行动错误，不产生假任务。
  - 所有内部阻塞原因先映射到固定公开 reason allowlist；阻塞通知通过 durable effect outbox 锚定、稳定幂等键和按 attempt 恢复重试。
  - 回调兼容改为签名检查，不再把回调内部 `TypeError` 误判为旧签名后进行无幂等键重发。
- Channel 与 Hire 自愈：
  - 关闭标志在状态检查后、revalidation/submit/challenge 续期前和 sleep 前均再次围栏。
  - 仅对具备完整自动激活历史、当前 Channel/Slash 证据、已提交 effects、不同 writer epoch 和精确关闭尾序列的 ACTION_REQUIRED 员工写入原子 phase-only recovery marker，再按 N+1 generation 重新校验；任何不完整或危险证据保持待处理。
  - fresh challenge 必须高于 recovery marker generation 才清除 pending，覆盖 Channel 启动后再次崩溃的窗口。
- Actor/Gateway 与异步桥恢复：
  - Supervisor 回放真实 `employee.actor.assignment_terminal`，合并 live/replay 终态时保留更丰富输出并对冲突默认拒绝；recover 全程阻止公共 submit，且拒绝进程内未决 owner。
  - Gateway 在判定未知派发结果前先读取 Actor 权威终态；完成但重启后只有 digest 的结果返回稳定 `employee_result_unavailable_after_restart`，不重复执行 ACP。
  - NLI bridge 增加 PID/thread/loop 所有权、at-fork 重置、启动 readiness 上限及 abort/stop/join/close 时序，迟到线程会自行停止，不遗留孤儿 loop。
- UI 预览更新为 Journal 当前团队、群关系降级、运行态与接单状态的分层展示。
