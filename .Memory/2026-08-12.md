# 2026-08-12 性能加固（阶段性收口）

## 已完成

- TaskScheduler 增加普通/系统队列独立容量（默认 1000/100）和终态历史上限（默认 5000）；准入在写入索引前原子完成，并持续清理空闲 chat/project/queue/running 索引，避免长期运行后无界增长。
- CardDelivery 建立可重试、幂等的 shutdown/drain 生命周期；registry 改为弱引用；普通编程自有 delivery 在成功、失败和 fallback 路径均回收。CardSession 在渲染前按不可变快照合并更新，并保护终态不被后续非终态覆盖。TimerScheduler 将慢回调移入有界执行器，关闭时统一排空或取消尚未开始的回调。
- 飞书卡片 action 的陈旧刷新和系统门禁提示改为 ACK 成功写回 WebSocket 后才提交的有界系统 follow-up；ACK 写入失败、handler 异常、关闭或容量不足时失败关闭且不做同步远程 I/O。相同 ACTIVE 项目且成员关系完整时仅刷新内存 LRU，跳过冗余快照重写/fsync。
- Workflow runtime 用 `AsyncLocalStorage` 建立词法 request collector lineage；并行 sibling race 互不取消，嵌套 descendant 仍继承父级取消边界。
- ACP 大型工具原文改为默认不捕获；仅 Workflow `AgentExecutor` 显式开启。该策略贯穿异步/同步会话、factory、compaction 和 failover，完整内容进入 Workflow 流时仍经过脱敏投影。

## 原因

- 限制长驻进程中的任务索引、线程/回调和原始工具载荷增长。
- 将昂贵卡片渲染及远程通知移出 ACK 热路径，并减少重复项目落盘。
- 修复并行 Workflow 的取消作用域串扰，同时保留全局取消与请求清理契约。
- 明确资源所有权和关闭栅栏，防止关闭返回后继续产生 I/O 或后台线程。

## 普通编程终态诊断与历史子代理对账

### 更改内容

- 修复终态错误卡无条件承诺“点击查看详情”但没有按钮的问题：只有绑定了诊断记录时才显示该提示与“查看详情”按钮；否则明确引导使用“查看状态”。
- 为普通编程失败、超时和异常终态注册与原始 chat/message 绑定的短期诊断 token；回调只返回经过脱敏和长度限制的结构化字段，不把原始工具输出或异常栈塞进卡片 action。
- 在 ACP 协作域新增最终 `list_agents` 权威证明跟踪。仅当任务正常 `end_turn`、没有未完成计划/外层工具/窗口耗尽，并且唯一异常是历史子代理记录未闭合、最终显式快照覆盖所有已观察子代理且均为终态时，将结果保持为“已完成”，同时显示黄色状态对账提醒和诊断入口。
- 新的 spawn/followup/activity 会立即使旧终态证明失效；未知或畸形身份/状态保持 fail-closed，真实未完成任务仍使用红色失败终态。
- 更新 `ux/programming-task-visibility.html`，增加“完成但需对账”和“真实未完成”两种终态预览，使绿/黄/红状态含义可直接审阅。

### 原因

- 原实现只写了折叠详情文案，`ProgrammingCardSession.fail()` 没有提供 `detail_action`，因此飞书端不存在可点击控件。
- 2026-08-12 的实例中，最终 `list_agents` 已确认 3 个子代理全部完成，但较早被中断的两代历史活动仍被结果分类器计作运行中；交付内容完整，属于状态对账告警而非任务失败。

- 新增诊断按钮绑定/回读、权威快照失效，以及最终快照/早期活动畸形证据 fail-closed 回归。

## Workflow 生成超时伪取消与飞书事件漏注册

### 更改内容

- 将 Workflow 级 `stop_event` 与每次脚本生成 ACP 会话的内部取消事件分离。单次尝试超时、传输失败或 fallback 清理只取消当前会话，不再把整个 Workflow 标成用户取消；真正的 `/stop_wf` 仍通过已绑定活动会话即时中断。
- 脚本生成代码默认上限与常量统一从 180 秒调整为共享 600 秒硬截止，并继续保留 120 秒有效活动 idle timeout；复杂生成只要持续产生有效活动即可继续，完全静默仍会提前退出。
- 主 Bot WebSocket dispatcher 显式消费已订阅的 `im.chat.member.bot.added_v1` 与 `im.message.reaction.deleted_v1`，避免 SDK 因 `processor not found` 返回错误并触发重复投递。

### 根因

- 2026-08-12 05:48 的 Workflow 在 A1 编排器运行 180 秒后触发 ACP hard cap。清理路径调用包装会话 `cancel()` 时把共享的 Workflow `stop_event` 置位，下一次 fallback 前的状态检查因此抛出 `_WorkflowGenerationCancelled`，卡片错误显示“已取消”；用户并未主动停止。
- 飞书应用清单订阅了机器人入群和表情删除事件，但主连接只注册了机器人退群和表情创建处理器，SDK 无法找到 processor。

### 验证

- TDD 回归先稳定复现三类失败：当前尝试取消污染 Workflow、两个订阅事件 processor 缺失、默认生成上限仍为 180 秒。
- Workflow 生命周期/生成可靠性与 WS/配置扩展组 214 passed。
- 全仓非慢速门禁 3289 passed、26 deselected、39 subtests passed；全量 Ruff、配置校验与 diff-check 通过。

### 后续风险

- 脚本生成仍受共享 600 秒总截止约束；到期后会明确进入失败而非伪装为用户取消。池内 fallback 只使用总预算剩余时间。

## 动态多 Agent Orchestration V3 改造方案

### 更改内容

- 新增 `docs/2026-08-12-dynamic-multi-agent-orchestration-v3-plan.md`，记录 GhostAP 从品牌/固定角色编排演进为后端中立、多 Agent 动态协作控制面的完整方案。
- 冻结核心决策：用户选择的是允许使用的资源池，角色属于任务节点；Planner 只提出类型化 PlanRevision，确定性 Kernel 独占能力过滤、权限、预算、调度、重规划和终态判定。
- 明确 Direct、Deep、Spec 保留原执行语义；Workflow 作为 V3 首个迁移入口；临时 ACP Agent 与持久 Employee 只共享 Resource/Dispatch 合约，不共享身份、会话、长期记忆或权限实例。
- 将实施拆成合约护栏、Backend Catalog、独立 Journal/Projection、typed planner、Workflow V3、验证重规划、隔离写、Employee Adapter、Saved Squad、旧路径退役十个可回滚阶段，并为每阶段列出文件、接口、测试和 commit 边界。

### 原因

- Codex、Grok、TraeX、Hermes、OpenClaw 等仅是示例资源；将品牌固化为规划者、实现者或评审者会限制未来 ACP 后端并造成错误能力推断。
- 当前 Workflow 已有冻结池和通用拓扑原语，但仍存在品牌推荐、运行时能力匹配缺失、字符串数据流、共享 cwd 并行写和非耐久控制状态等缺口；Employee Team 又有固定 execute/review/revise 阶段，不能直接充当通用编排内核。
- 复用 Employee Journal/Effect 技术不等于复用 Employee 身份域；独立 OrchestrationStore 可以保留耐久性，同时避免临时调用污染员工长期上下文或扩大单写 Journal 故障域。

### 验证

- 回读 942 行计划文档并检查标题、阶段、接口、回滚和验收矩阵完整性。
- 扫描占位词与品牌写死表述；唯一固定品牌流水线表述位于“明确否决”示例中。
- 校验所有已存在关键模块路径，修正 BlobStore 引用为 `src/autonomous/journal/blob_store.py`。
- `git diff --check -- docs/2026-08-12-dynamic-multi-agent-orchestration-v3-plan.md` 通过。
