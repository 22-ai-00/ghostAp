## 管理员项目任务的 ACP 个人可信租约

### 根因

- `ACP_PERMISSION_AUTO_APPROVE=true` 只处理 ACP 的批准回调，并不改变提供方自己的
  sandbox。官方 `@agentclientprotocol/codex-acp@1.2.0` 默认 `agent` 模式仍是
  `workspace-write + networkAccess=false`；因此远程 `git push` 即使能选中
  `allow_once`，仍会频繁触发网络/主机边界。
- GhostAP 的批准桥还会再次经过 tool filter、危险命令和 SandboxExecutor 检查；
  这对多用户/Employee/Workflow 必要，但单人管理员在当前项目里的普通编程任务
  没有可审计、可自动撤销的放宽入口。

### 修复

- 新增默认关闭的 `ACP_TRUSTED_PERSONAL_MODE` 与显式风险确认
  `ACP_TRUSTED_PERSONAL_ACK`。安全姿态在缺少确认或管理员时阻断；有效启用时使用
  稳定 warning finding `acp_trusted_personal_active`。
- 权限只在“普通编程 + 已绑定项目 + 当前 sender 属于 `ADMIN_USER_IDS`”时生效。
  Workflow、Employee、非管理员和无项目任务继续使用原策略。
- 每个用户任务创建独立权限租约。官方 Codex 在执行窗口开始前通过 ACP config
  切到 `agent-full-access`，从而真正打开网络与主机访问；任务结束恢复启动前的
  `agent` / `read-only` 模式。其他 ACP 提供方在同一租约内绕过 GhostAP 的二次
  permission gate，但仍优先选择一次性批准。
- 自动续窗、死会话替换和 provider session resume 都重新获取同一任务租约。
  撤销失败或状态不确定时把会话标为 force-dead 并立即退休，禁止全权限状态进入
  下一任务。
- `.env.example` 与 README 补充单人部署说明；本机 `.env` 已显式启用两个开关，
  `.env` 继续保持 gitignore，不提交环境值。

## COT 最终 wire 边界导致大结果提前降级修复

### 现场根因

- 前一轮已经把工具正文限制为 4000 bytes、Update body 限制为 16 KiB，但真实租户
  仍在第一个大工具结果附近返回 `code=10001`；随后 adapter 将 COT 标记为
  `sink_unhealthy` 并切回 Card 2.0。Create、RUN_STARTED 和此前的小 Update 都成功，
  因此不是权限、能力开关或超时问题。
- 官方 Lark Go/Python SDK 的生成 `MessageCot` 模型给出了此前遗漏的真实约束：
  `content` 是完整事件详情 JSON 字符串，**单条最长 4096 字符**；`timestamp` 类型是
  字符串。旧实现只裁剪 `TOOL_CALL_RESULT.content` 内层正文，没有计算
  `messageId/toolCallId/role` 与 JSON 转义外壳。4000 字节 ASCII 结果编码后稳定超过
  4096 字符，恰好解释现场只在大结果处失败；反斜杠、引号和换行还会进一步放大。
- `TOOL_CALL_ARGS` 也可能在裁剪后失去 JSON 合法性；用户初始需求、文本/推理 delta
  和 RUN_ERROR 同样缺少最终双层 JSON 边界，属于同一类潜在提前降级入口。

### 修复

- `src/feishu/cot.py` 将 4096 字符限制放在最终 `events[].content` 编码结果上统一
  fail-closed 预检，并把 wire `timestamp` 规范为官方字符串类型；直接 API 调用传入
  的非负整数时间戳会在出站前归一为字符串。
- 文本与 reasoning delta 同时按 UTF-8 字节和最终 JSON 字符边界无损分帧，转义字符
  不再让单帧越界；工具结果、RUN_STARTED query 和 RUN_ERROR message 依据各自完整
  外壳计算可用空间后裁剪。
- 工具参数先清洗并压缩成合法 JSON；超长或非 JSON 输入改为有界、合法的
  `truncated/summary` JSON 参数，避免半截 JSON 触发服务端业务拒绝。
- 业务拒绝日志在保留错误码之外增加经过脱敏和单行限长的服务端 `msg`，后续遇到
  新协议错误可直接定位，同时不泄露工具内容或凭据。

  本地拒绝、字符串时间戳、反斜杠/引号/换行无损分帧、超长合法工具参数摘要、长
  RUN_STARTED query 和脱敏业务错误详情回归。

## COT 大工具结果与收尾频繁降级修复

### 现场根因

- 真实租户最近两次 Codex 运行都在首个大工具结果后将 COT 标记为 `sink_unhealthy`，回放缓存分别为 11/12 个事件、约 20.6 KiB；Create、RUN_STARTED 与之前的小过程帧已经成功，因此不是能力未开通。
- `TOOL_CALL_RESULT` 额外发送了 AG-UI 标准未定义的 `status` / `isError`，工具内容沿用卡片侧 8000 字符上限；文本与推理也没有单帧或 Update body 字节边界。真实飞书业务拒绝只保存在 session 内，日志仅剩 `sink_unhealthy`，无法现场看到错误码。
- Update 单请求预算只有 2 秒；1.2 秒收尾总预算又平均拆成约 0.4 秒的 drain/terminal/Complete 阶段。现场 Complete 在本地超时后约 0.9 秒晚到成功，证明该预算会把正常飞书延迟误判为降级。

### 修复

- `TOOL_CALL_RESULT` 收敛为标准 `messageId/toolCallId/content/role` 四字段；工具成功/失败语义保留在清洗后的 `content` 与主卡权威状态，不再发送未声明扩展字段。
- 文本和 reasoning delta 按 UTF-8 安全拆成不超过 4000 bytes 的无损事件；单个工具参数/结果按 UTF-8 截断到 4000 bytes；worker 再按 14 KiB 事件预算拆分 Update，包含 message/cot ID 后的实际请求保持不超过 16 KiB，并严格保留 FIFO。
- session 默认单请求预算 2→5 秒，收尾总预算 1.2→4.5 秒、单阶段约 1.5 秒（显式上限 6 秒）；仍保持有界失败与不确定请求不盲重试。
- 异步 Update 首次失败新增脱敏 `stage=update/failure/code/batch_events` 日志，后续可直接区分业务拒绝、超时和 SDK 故障。

### 验证

- `tests/test_feishu_cot.py`：`49 passed`，新增标准字段、中文 UTF-8 字节边界、长文本无损分帧、16 KiB 请求边界、大工具结果截断、真实业务错误码日志回归。
- 普通编程降级/终态扩展回归：`149 passed`。
- `uv run ruff check src/feishu/cot.py tests/test_feishu_cot.py` 与 `git diff --check` 通过。

## 普通编程切换为飞书原生 COT 过程消息

### 背景与范围

- 参考用户提供的 Feishu Message COT OpenAPI / AG-UI 说明，将普通编程模式原先卡片内的文本、过程摘要和工具调用迁移到原生 COT 消息。
- 保留 Card 2.0 作为任务事实与结果权威面：多任务列表、当前任务、并行 Agent 摘要、图片和最终结论继续使用现有主卡；Deep、Spec、Workflow 与 Employee 的结构化卡片及恢复契约均未改线。
- 在 `ux/programming-cot-hybrid.html` 增加运行中、完成态与降级态预览，先固定产品边界再接生产代码。

### 实现

- 新增 `src/feishu/cot.py`：
  - 使用官方 `lark-oapi` 的 `BaseRequest` / `Client.request` 通用入口调用 Create、Update、Complete；当前锁定的 `lark-oapi==1.7.2` 只有 `MessageCot` 数据模型，没有生成式 COT resource，请求未绕过官方 SDK 手写 HTTP。
  - 严格校验 HTTP、SDK 与业务三层响应；`events[].content` 做 AG-UI 要求的双层 JSON 编码，使用单调毫秒时间戳、稳定不透明 ID，并清洗工具内容与错误文本。
  - Create、Update、Complete 在网络前执行主 Bot 出站审计和 managed trust revision 双重栅栏；绑定冻结原消息、chat、message/cot ID 与别名来源。
  - 单任务 FIFO worker、有界队列与批处理只接受 TEXT、REASONING、TOOL 事件；PLAN、图片、AgentSummary 和终态结论不会误入 COT。
  - session 单请求预算为 2 秒，权威关闭总预算为 1.2 秒（显式最大 1.5 秒）；可选 COT 不再长期拖延最终卡。
  - SDK hard-timeout 保留 pending attempt，由固定后台池按原顺序处理晚成功；技术性 RUN_STARTED / Update 降级以中性的 RUN_FINISHED(paused) + Complete(done) 收口，真实父任务终态仍按完成、失败或取消映射，Complete 不盲重试。Create 已成功但响应 ID 丢失时因接口无幂等键或查询能力无法安全补偿，这是协议残余，当前禁止猜测性重试并自动使用卡片结果面。
  - abort 先本地 fence 再异步收尾；STARTING/close 竞态、队列排空超时、未发送多批事件和 worker append 失败均有唯一终态 owner，worker 不依赖调用方再次 complete/abort 才退出。
- 在 `src/card/protocols.py` 增加抽象 `ProcessEventSink`，`ProgrammingCardSession` 只依赖协议，不导入飞书实现。
- `ProgrammingCardSession` 采用 visible-first：先确认原主卡可见，再激活 COT；Create/RUN_STARTED 失败沿用同一卡继续流式执行，ACP 不重跑。
- COT 成功时过程事件进入原生消息，卡片只补最后一个非空主 Agent 结论；中途 Update、队列、Complete 或异步健康失败时，最多缓存 2048 个 / 2 MiB 已清洗 CardEvent 并原子精确回放到卡片，当前事件不重复。
- 处理器关联 origin、主卡和 COT 两个 message ID；COT 激活后的执行入口异常会同时 abort 卡片/COT、原异常透传，不触发非流式 ACP 重跑。
- 新增 `FEISHU_COT_ENABLED` 正式配置，默认开启；租户未开放能力时每个任务自动回退现有卡片，可用该开关紧急回滚。

## COT 过程旁路降级不再误报任务失败

### 根因

- 普通编程主卡与飞书原生 COT 是两个独立状态面：主卡承载权威任务状态，COT 只传输过程记录。
- COT 单请求采用 2 秒预算；异步 Update、创建后的 RUN_STARTED、队列或收尾传输失败时，adapter 会把已接收过程原子回放到主卡并继续 ACP，但旧实现同时调用 `abort()`，把非权威传输故障映射成 `RUN_ERROR + Complete(error)`，因此 COT 很快显示“任务失败”，主卡却仍正常运行。
- 迟到 Create / RUN_STARTED 清理与 terminal append 失败也曾硬编码 `error`，会让过程通道状态覆盖随后到达的真实父任务终态。

### 修复

- 主卡确立为任务终态唯一事实源。真实 `COMPLETED`、`FAILED`、`CANCELLED` 继续映射其实际终态；COT abort、传输失败、超时和迟到清理统一以中性的 `RUN_FINISHED(status=paused) + Complete(done)` 收口，不再声称任务失败。
- COT 文案改为“过程记录中 / 过程记录完成 / 过程展示已切换到主卡”；即便真实错误 wire 由平台选择 error 文案，也只显示“过程记录异常结束，请查看主卡”。
- 明确的 RUN_STARTED 服务端非零响应才补发配对的 `RUN_STARTED + RUN_FINISHED(paused)`；连接丢失或响应不确定时禁止盲目重发，避免重复远端生命周期。
- adapter 降级时只回放一次已缓存过程并显示一次 info banner，主卡保持 running；日志仅记录固定 reason、事件数和字节数。父任务完成、失败或普通取消时清除运行中 banner，TTL / 显式 persistent 警告仍可保留。
- 普通编程卡的 `WARNING_UPDATED` 改为通用结构事件，不再被 Spec engine guard 丢弃，也不会被动创建 `EngineExtState`；保活按钮按 action ID 去重、替换和清除。
- `ux/programming-cot-hybrid.html` 补齐第三个“过程通道降级、主卡继续执行”预览态，并明确 COT 是非权威 sidecar。

## ACP 混合未完成状态按子代理优先续跑

### 根因

- 普通编程 Agent 自然 `end_turn` 时，续跑状态机原先只处理“仅有未完成计划”或“仅有未终态子代理”两种状态。
- 现场同时存在 `pending_plan_entries=3` 与 `unresolved_child_tool_calls=9`，两个互斥条件都不命中，因此 `automatic_continuations=0`，父任务直接以 incomplete 收口；卡片投影随后把仍未终态的子代理显示为“未收到最终结果，主任务已结束”。

### 修复

- `src/acp/continuation.py` 改为 child-first：只要所有未完成工具都来自子代理生命周期且没有外层工具仍在执行，就先进行一次权威状态对账，不再要求计划数为零。
- 对账轮严格限定为 `list_agents -> wait_agent -> list_agents`，禁止中止、取消、重复实施或改写原计划；一轮后仍有 running/pending 子代理时保持 incomplete，不让主 Agent 与活跃子代理重复工作。
- 每次 child reconciliation 都冻结并恢复进入该轮前的原计划，包括 `None`、已完成和 pending 三种状态。对账输出及会话证据 enrichment 均不能抹除旧计划，也不能凭空注入新计划。
- 子代理全部终态后才进入既有计划续做；继续沿用绝对 deadline、最多 1 次子代理对账和 3 次计划续做，避免无界循环。

### 验证

- `uv run python -m pytest tests/test_acp_continuation.py tests/test_acp_finalization.py tests/test_acp_execution_windows.py tests/test_acp_client.py -q`：`145 passed`。
- `uv run ruff check src/acp/continuation.py tests/test_acp_continuation.py` 与相关 `git diff --check` 通过。
- 回归覆盖 mixed→子代理终态→计划完成、子代理仍运行、外层工具仍运行、对账轮篡改/新增计划，以及 child 1 次 + plan 3 次的有界上限。

## 未对账子代理不再伪造失败或取消终态

### 根因

- 普通编程父任务以 incomplete、异常、超时或完成收口时，`ProgrammingCardSession` 会统一结束主卡；旧投影同时把所有仍为 running/pending 的子代理强制改成 `failed` 或 `cancelled`。
- 父任务结束只能证明本地不再等待，不能证明子代理真实失败或被取消；因此截图中的失败/取消统计混入了本地推断，并非权威子代理终态。

### 修复

- `finalize_summaries` 只保留提供方已经确认的 `completed`、`failed`、`cancelled`。仍未收到终态的子代理改为独立 `unresolved` 展示态，进展固定为“未收到最终状态，主任务已结束”，并清除非权威错误残留。
- `unresolved` 不计入运行、失败或取消；子代理面板用问号图标和“未收到最终状态”单独统计。主卡仍按真实 incomplete 进入 failed 终态，不会继续显示执行中。
- 未改动有界续跑策略；该展示态只在既有自动对账/续做预算耗尽、父任务已经确定收口之后使用。
