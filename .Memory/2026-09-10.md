## 模型选择卡：为什么有些机器是按钮、有些是下拉框

### 直接分流条件

- `src/card/builders/system.py` 构建模型卡时计算
  `has_dimensions = bool(state.profiles or state.efforts)`：
  - 为真 → 渲染 3 个 `select_static` 下拉框（模型 / profile / reasoning effort）；
  - 为假 → 每个模型渲染一个 button，外加"使用默认"按钮。
- `profiles/efforts` 来自 `ACPModelOption.selection_variants`
  （`src/acp/options.py`）：只有 CLI/ACP 真的声明了可选变体时才非空。

### 各后端差异

- `codex` / `dsh`：逐模型探测 `reasoning_effort`，探测成功才有下拉。
- `traex`：读本机 `~/.trae/cli/models_cache.json`，恒至少合成 `standard` profile，
  因此基本总是下拉。
- `claude` / `gemini` / `grok` / `aiden` / `coco`：扁平映射，没有变体，永远按钮。
- 注意 CLI 形态的 `claude`（本机 shell 桥接）不走 ACP 发现：
  `fetch_acp_models` 对 CLI 后端直接 `_fallback()`。

### 机器间不一致的 7 个来源

1. CLI 是否安装 / 登录 / 版本差异；
2. 逐模型探测超时（`acp_model_probe_timeout` 默认 15s），慢机器探测失败→按钮；
3. traex 本机缓存文件 `~/.trae/cli/models_cache.json` 是否存在与内容；
4. ACP 能力声明差异（如 dsh 的 `@dsh-enhanced/acp` 插件版本）；
5. 内存缓存（正结果 1800s、负结果 300s，键为 `(tool, cwd)`；codex 同样 1800s）；
6. checker/slug 上的 `@lru_cache`：刷新卡片不会清，必须重启进程；
7. `build_clean_env` 造成的 HOME / PATH / 网络环境差异，导致探测结果不同。

## 修复 watchdog 继承管道 flaky 测试（提交 `587cd24b`）

- `test_cli_watchdog_kills_descendant_that_inherits_stdout` 曾持续 flaky
  （干净 dev 约 1/3 失败率），已修复并保留——它用真实进程覆盖
  `process_cleanup.py` 的核心事故场景：只杀忽略 SIGTERM 的 CLI leader，
  继承 stdout 的 descendant 会让读端永久阻塞，必须 killpg 整组。
- 根因全在测试自身的时序赌博，生产 watchdog/进程组收敛逻辑无缺陷：
  1. leader-running 形态 `prompt_timeout=0.2s`，deadline 在 Popen 返回
     即刻起算，而新 Python 解释器冷启动（import + spawn child + flush
     ready）在繁忙机器上可超 0.2s，ready 没进 chunks 即断言失败；
  2. 更隐蔽的第二层竞态：`spawn_descendant` 里 `process.wait(timeout=1)`
     在 patched Popen 调用栈内同步等 leader 冷启动退出，CPU 打满时
     TimeoutExpired 穿透 Popen 被生产外层捕获 → 误报 `stop_reason="error"`
     （leader-exits 形态）。
- 修法：leader flush ready 后 touch marker 文件，测试屏障等到 marker 才让
  生产 deadline 起算（两个 barrier 预算统一 30s，只约束探针挂死）；
  leader-running 的 prompt_timeout 0.2→2.0s（验证的是组 SIGKILL 收敛路径
  而非超时精度）；worker.join/回收护栏 1.5s/1s → 10s/30s。
- 验证方法值得复用：128 路 `yes` 打满 64 核 + 4 路 pytest 并行互抢 CPU
  连压 60 次（单测耗时被拉到 5–14s）0 失败，普通负载 30 次 0 失败。
