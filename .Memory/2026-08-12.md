# 2026-08-12 性能加固（阶段性收口）

## 已完成

- TaskScheduler 增加普通/系统队列独立容量（默认 1000/100）和终态历史上限（默认 5000）；准入在写入索引前原子完成，并持续清理空闲 chat/project/queue/running 索引，避免长期运行后无界增长。
- CardDelivery 建立可重试、幂等的 shutdown/drain 生命周期；registry 改为弱引用；普通编程自有 delivery 在成功、失败和 fallback 路径均回收。CardSession 在渲染前按不可变快照合并更新，并保护终态不被后续非终态覆盖。TimerScheduler 将慢回调移入有界执行器，关闭时统一排空或取消尚未开始的回调。
- 飞书卡片 action 的陈旧刷新和系统门禁提示改为 ACK 成功写回 WebSocket 后才提交的有界系统 follow-up；ACK 写入失败、handler 异常、关闭或容量不足时失败关闭且不做同步远程 I/O。相同 ACTIVE 项目且成员关系完整时仅刷新内存 LRU，跳过冗余快照重写/fsync。
- Workflow runtime 用 `AsyncLocalStorage` 建立词法 request collector lineage；并行 sibling race 互不取消，嵌套 descendant 仍继承父级取消边界。
- ACP 大型工具原文改为默认不捕获；仅 Workflow `AgentExecutor` 显式开启。该策略贯穿异步/同步会话、factory、compaction 和 failover，完整内容进入 Workflow 流时仍经过脱敏投影。

## 原因

- 限制长驻进程中的任务索引、线程/回调和原始工具载荷增长。

- 明确资源所有权和关闭栅栏，防止关闭返回后继续产生 I/O 或后台线程。

## Workflow 生成超时伪取消与飞书事件漏注册

### 更改内容

- 将 Workflow 级 `stop_event` 与每次脚本生成 ACP 会话的内部取消事件分离。单次尝试超时、传输失败或 fallback 清理只取消当前会话，不再把整个 Workflow 标成用户取消；真正的 `/stop_wf` 仍通过已绑定活动会话即时中断。

### 根因

- 2026-08-12 05:48 的 Workflow 在 A1 编排器运行 180 秒后触发 ACP hard cap。清理路径调用包装会话 `cancel()` 时把共享的 Workflow `stop_event` 置位，下一次 fallback 前的状态检查因此抛出 `_WorkflowGenerationCancelled`，卡片错误显示“已取消”；用户并未主动停止。
- 飞书应用清单订阅了机器人入群和表情删除事件，但主连接只注册了机器人退群和表情创建处理器，SDK 无法找到 processor。

### 验证

### 深度审查后的可靠性加固

- **Ingress/Router handoff**：将主 Bot 对 Employee response ownership 的观察收敛为 `OWNED`、`DURABLY_DENIED`、`INVALID_UNKNOWN`、`PENDING` 四态，逐字段绑定 acceptance、envelope、dedup、payload digest、transport generation 和冻结 authority。等待改为 epoch event，不再依赖容易丢唤醒的 Condition timeout 重入；`deadline=None` 只观察当前线性化点，有限 deadline 和 `timeout=0` 都会执行一次真实 Ingress/Router 投影并保留精确 deny/unknown 语义。
- **耐久 Main-Bot 告警**：Employee handoff unknown/denied 与 scheduler pre-start terminal 路径新增加密 Blob + Journal warning Outbox，PREPARED/EXECUTING 在外呼前 fsync 锚定，COMMITTED/ACTION_REQUIRED 记录明确终态；稳定 origin UUID、防重复投递、重启恢复、毒记录隔离和旋转公平队列防止早期失败告警饿死后续记录。飞书永久错误与 retryable/unknown 传输结果使用类型化分类；共享 reporting lane 中的 warning 批次只使用 0.25 秒绝对预算，卡死 transport 不再阻塞后续终态补报与 Employee Outbox。
- **Dispatch reporting 与 Employee Outbox**：终态补报从主 dispatch 循环拆到独立 lifecycle worker；恢复结果结构化返回 repaired/deferred attempts，只隔离明确的 BlobPublish/BlobRead/BlobMissing/KeyResolution 类 record-local deferred，Journal/投影/程序错误仍立即传播。投递队列加入公平轮转、receipt 坐标核验、单记录 poison 隔离和有界 close/drain；reporting worker 的并发 `start/start`、`start/close` 由单独 lifecycle lock 线性化。
- **Hire/Fire/成员关系外部副作用**：增加每 employee 外部 mutation gate。Fire 必须先锚定 retirement fence 再等待/阻止 registrar、vault、slash、Channel 和 membership ADD；lease 覆盖真实 async child 终态而非仅覆盖 caller future。历史 ADD 只有在因果上更晚的 REMOVE COMMITTED 后才视为清理，正向成员探测也先锚定 ADD PREPARED/EXECUTING。启动恢复在 actor/router/team/fire 和 runtime-ready 之前执行 projected membership audit，失败以 `membership_audit` blocker 明确拒绝执行。
- **任务与关闭竞态**：TaskScheduler run ID 改为唯一，terminal completion 与 cancel/timeout 竞争保持一次权威终态，控制 gate 等待可取消且 listener 安全释放；Employee Channel readiness 使用验证后冻结的 app/generation/connection 快照。关闭共享 reporting/warning 的 drain 预算，不为第二个阶段重新发放完整 timeout；持锁等待、Journal commit 和同步 transport 均须服从同一 monotonic deadline，未确认外呼不伪造成功或重复发送。
- **Admission 与恢复边界**：补齐 hire 输入在 admission 前的全量验证、既有 App/名字并发唯一性、归档名字释放、队列 handoff fence、不可读 ingress 的有界重试与终态收敛、retirement delivery-only Channel 和外部清理恢复。任何测试失败、缺失终态或异常退出均作为真实缺陷追踪，没有通过 skip/过滤器掩盖。

## Team 与 Ingress 共享 Blob 恢复闭环

## Ingress 失败清理与共享 Blob retain 并发闭环

- 根因：Ingress Blob publish/readback 失败使用 `before_ids`/目录现状差集识别待隔离对象，但差集扫描和隔离没有与共享 Blob retain 注册串行；Team 在两者之间 publish+retain 时，Ingress 会把并发 Team Blob 误当成本次失败产物，造成已锚定 `team.v2.run.created` 引用不可读。

## Team Coordinator 有界关闭

### 更改内容与原因

- 根因：`TeamCoordinatorActor.close()` 直接调用 `ThreadPoolExecutor.shutdown(wait=True)`；当 backend `result()`/`cancel()` 或 coordinator session close 卡住时，Employee runtime 会无限阻塞在 Team close，无法进入后续有界 drain 或安全保留共享依赖。
- Team 首次 close 现在原子关闭 admission，并保存每个 `run_id -> Future`；排队 Future 使用 `cancel_futures=True` 取消，done callback 精确清理 `_active`，运行中 Future 使用同一 monotonic deadline 有界等待。
- decision provider 的同步 close 由唯一 daemon cleanup thread 执行，并复用同一绝对 deadline；重复 close 观察同一 worker/provider cleanup，完成后幂等成功，不会重复关闭 provider。
- 超时统一抛出 `TeamCoordinatorCloseTimeout`。`EmployeeTeamService` 透传 timeout，`EmployeeDepartmentRuntime.close()` 把该 typed failure 计入 `team_service` 与 `dependent_resources_held`，不继续销毁 Journal、Outbox、Vault 等共享依赖。

### TDD 与验证

- RED 依次证明：旧 actor 不接受 `timeout_seconds`；runtime 仍无参调用 Team close；blocking decision provider close 会越过 20ms deadline；排队任务无法被可靠清出 `_active`。
- GREEN 专用回归 3 passed：双 running + 单 queued 的有界取消/重试、runtime shared dependency 保留、provider cleanup 同 deadline 且只执行一次。
- Team recovery、共享 Blob、collaboration 与 close 聚焦组 24 passed；扩大 Team/runtime 组合在共享 Outbox close 并发修改前达到 125 passed，目标 Ruff、`uv run ruff check src/autonomous` 与 `git diff --check` 通过。最终全仓门禁由主线在所有并发改动落稳后统一重跑。
