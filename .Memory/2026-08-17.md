## Employee reporting Journal 热循环修复

- 现场采样确认 `employee-durable-reporting` 是此前约 65% 单核常驻 CPU 的
  来源：每个 reporting tick 都经 `EmployeeFireService.list_states()` 调用
  `JournalWriter.replay()`，反复读盘、验 HMAC 并 JSON 解码 5 MiB、3996 帧
  的 Employee Journal。
- 将 Fire 的状态读取、提交前检查、外部变更 fence 恢复统一改为
  `JournalWriter.committed_tail(1)`。该 tail 由进程内唯一 writer 在加载和
  每次锚定提交时维护，仍以 Journal/anchor 为唯一事实源，不新增可写缓存，
  也不放宽断链或 anchor 不匹配检查。
- 同步调整跨服务游标推进回归，显式证明活跃 drain 使用 committed tail，
  空闲 drain 不访问 Journal，且 Fire 路径不再退回全盘 replay。

## 主 Bot 审计 Journal 快速恢复

- 根因是 `MainBotSendAuditLog.open()` 使用通用 `JournalWriter.open()`，
  启动时把 382 MiB、382771 帧逐帧 JSON 解码、重建 canonical payload、
  校验 HMAC 并全部常驻 `_frames`；其中 379788 帧是高频卡片 patch。
- 为严格的单 aggregate 追加账本新增 `open_at_verified_tail()`：流式扫描
  原始物理帧并核对每一帧的 SHA-256 `previous_hash` 链、帧数、外部 anchor
  和尾帧 HMAC，但只物化已锚定尾帧及其 aggregate version。每次新提交后
  也只保留最新帧，因此没有删除、迁移或压缩任何历史审计证据。
- `replay()` 保持原有完整 JSON/HMAC 验证，用于真正的历史计数查询；查询
  期间发现任何损坏会将审计标为 incomplete，后续 activation fence
  fail-closed。专用 writer 同时拒绝其他 aggregate，并拒绝从内存 tail
  冒充完整 `committed_tail`。

## Employee Channel uv Python 沙箱挂载修复

- Autonomous 全量回归暴露出 Linux bwrap 启动偶发退回未验证进程隔离。
  `strace` 确认沙箱内执行 `.venv/bin/python` 时返回 `ENOENT`：虚拟环境的
  解释器是指向 uv 基础 Python 的绝对符号链接，而原实现只读挂载
  `.venv`，没有挂载链接的真实运行时和词法目标路径。
- bwrap 根现在同时只读挂载 `sys.prefix`、`sys.base_prefix`，并在两者因
  `/home` 到 `/data00/home` 等主机别名而不同时，将基础运行时映射到解释器
  符号链接保留的词法目标；仍只暴露 Python 运行时，不暴露用户目录。
- 对位于 repo 外（测试中位于空 `/tmp` tmpfs）的注入 worker，只创建父
  目录骨架并只读绑定单一 worker 文件，避免暴露宿主临时目录的其他内容。
